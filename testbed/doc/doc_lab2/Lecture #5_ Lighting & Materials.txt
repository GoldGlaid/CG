Освещение
Для выполнения операций освещения необходимо определить, сколько света доступно в сцене. Для этого требуется смоделировать источники света и добавить их как-то на сцену
В традиционных системах освещения  используются 3 различных абстрактных типа, которые представляют различные ситуации освещения: 
точечные источники света
прожекторные источники света
направленные источники света

Направленный источник света – моделируется как бесконечно удаленный, поскольку все его лучи света имеют одно и то же направление; оно не зависит от местоположения источника света
Направленный источник света
Когда источник света находится далеко, лучи света, исходящие от него, почти параллельны друг другу
Кажется, что все лучи света исходят из одного направления, независимо от того, где находится объект и/или наблюдатель
Хорошим примером направленного источника света является наше солнце

Точечный источник света
Точечный источник света — это просто точка в пространстве, которая излучает свет равномерно во всех направлениях вокруг себя
Точечный источник света имеет:
положения в пространстве
количества излучаемого им света
сила затухания
Сила затухания используется для определения того, как яркость света уменьшается по мере удаления от источника света (пропорционально квадрату расстояния)

Прожекторный источник света
Прожекторный источник света — это источник света, расположенный в пространстве, который вместо того, чтобы излучать лучи света во всех направлениях, излучает их только в определенном направлении
В результате освещаются только объекты, находящиеся в определенном радиусе от направления прожектора, а все остальное остается в темноте
Примером прожектора может служить уличный фонарь или фонарик

Мы уходим от push constants!
Механизм push constants был очень полезен, когда нужно было быстро пробросить невершинные данные в шейдеры, например матрицы
Одной командой можно было скопировать данные из RAM в VRAM без головной боли и аллокаций буферов
У push constants существуют жесткие ограничения по размеру и, в зависимости от вендора GPU и драйвера, этот размер может быть 128 байт – самый маленький по спецификации Vulkan API
Push constants не поддерживают массивы, а они нам нужны, поскольку инфу про источники света мы должны брать извне и их у нас не фиксированное количество
Теперь познакомимся с системой descriptor set и использованием буферов для хранения произвольного количества данных!
Приготовились! Будет ЕЩЁ БОЛЬШЕ кода на Vulkan!

Descriptor pool (пул дескрипторов ресурсов)
Descriptor pool описывает, какие внешние для шейдеров ресурсы можно выделить и сколько

Как теперь жить?
Вспоминаем, что функции vkCmdXXX только лишь записывают команды, а не исполняют их!
Исполнение этих команд будет произведено после вызова функции VkQueueSubmit (эта функция используется в veekay.cpp в конце цикла программы и исполняет команды, которые были записаны в функции render вашего приложения)
Поэтому если мы рисуем больше одного объекта, то применится последнее копирование в буфер, потому что оно там оказалось сразу после VkQueueSubmit 
vkCmdPushConstants мы убрали, менять данные во время записи команд теперь нельзя
Именно поэтому мы выделили буфер моделей достаточно большим и сделали его UNIFORM_BUFFER_DYNAMIC, чтобы при vkCmdBindDescriptorSets можно было выбрать сдвиг в этом буфере, который соотносится с данными о конкретной модели

Освещаем освещением в фрагментном шейдере
void main() {
	vec3 normal = normalize(f_normal);

	vec3 view_dir = normalize(view_position - f_position);
	vec3 half_vector = normalize(view_dir - sun_light_direction);

	float sun_shade = max(0.0f, -dot(sun_light_direction, normal));
	vec3 sun_diffuse = f_color * albedo_color;
	vec3 sun_specular = specular_color * 
                        pow(max(0.0f, dot(normal, half_vector)), 
                            shininess);
	vec3 sun_light_intensity = sun_shade * sun_light_color * 
                               (sun_diffuse + sun_specular) ;

	vec3 color = ambient_light_intensity + sun_light_intensity;
}
